# 🎤 ポートフォリオ活用ガイド:書類選考・面接でどう伝えるか

このドキュメントは、案件01〜09の教材と実際に行った演習を、**転職活動(書類選考・面接)でどう伝えるか**をまとめたものです。2026年9月11日時点で、このリポジトリには本人の実行証跡・独力説明の記録は未掲載です。以下の実施後の説明例は本人の実績ではありません。実行した案件と確認できた結果だけを記載してください。

> 💡 **前提**: このガイドは案件01〜09をひととおり終えた(あるいは進めながら並行して読んでいる)方を想定しています。まだ着手していない方は [docs/00_roadmap.md](00_roadmap.md) から始めてください。

## 1. 準備の全体像 🗺️

書類選考から面接までの準備は、演習と同時並行で進めるのが最も効率的です。案件が終わってからまとめて準備しようとすると、作業当時に考えていた「なぜこの設計にしたか」を忘れてしまいがちだからです。

```mermaid
graph LR
    A["各案件を実施"] --> B["作業中にスクリーンショットを保存"]
    B --> C["案件README末尾の<br/>振り返りを自分の言葉で書く"]
    C --> D["職務経歴書・GitHub<br/>プロフィールを整備"]
    D --> E["想定質問への回答を準備"]
    E --> F["書類選考・面接"]
    F -.振り返りを更新.-> C
```

案件をひとつ終えるごとに B → C を済ませておくと、9案件終了時点でほぼ準備が完了している状態になります。

## 2. 職務経歴書・GitHubプロフィールでの見せ方 📝

### 2-1. 職務経歴書での書き方

未経験からの応募の場合、職務経歴書に「実務経験」として書くことはできません。しかし「自己学習・ポートフォリオ制作」という項目を設けて、実務に近い形で経験を積んだことを具体的に記載することは十分に効果があります。

| 項目 | 書き方の例 |
|---|---|
| タイトル | 自己学習:オンプレミス(クラウドではなく、自社内に機器を設置・運用する形態)想定のネットワーク・サーバー構築ポートフォリオ(全9案件) |
| 期間 | 20XX年X月〜20XX年X月(実際に取り組んだ期間) |
| 概要 | 架空のIT保守運用会社の新人インフラエンジニアという設定で、成長企業からの依頼に対しLAN設計・VLAN分割・NAT/FW構築・Webサーバー公開・監視冗長化までを一人称で対応 |
| 使用技術 | Cisco Packet Tracer、Ubuntu Server、Apache/Nginx、BIND9、ISC DHCP、Samba、OpenSSH、OpenVPN、Zabbix、keepalived など |
| 成果物 | GitHubリポジトリ(URLを記載)、全案件README、構成図、設計書 |

上の表は全9案件を実施・記録した場合の例です。教材を読んだ段階は「学習中」、設計だけなら「設計資料を作成」、実機で確認した項目は「本人環境で確認」と書き分けます。使用技術の一覧も、本人が扱って確認したものに絞ってください。

ポイントは、**「何を使ったか」に加えて「何を確認できたか」を書く**ことです。例えば監視なら「架空案件の監視を学習し、本人VMでサービス停止後に異常が表示されることを確認した」のように、実施日・結果・証跡へのリンクを添えます。冗長化や業務上の効果を未検証のまま実績に含めないようにします。

### 2-2. GitHubプロフィールでの見せ方

- リポジトリのトップに **README.md** を用意し(このパックはすでに用意済みです)、「誰が・何のために作ったか」を最初の数行で説明する
- GitHubプロフィール(自分のユーザー名のREADME)にこのリポジトリをピン留め(Pinned repositories)し、一言紹介文を添える
- 教材全体の設計を見るための[案件09](../projects/case09_capstone/README.md)と、本人の実行結果・説明記録への導線を分ける
- READMEのバッジ(status / level / topicsなど)は、リポジトリの中身を一目で伝えるための工夫として面接でも話題にしやすい

## 3. 「なぜその設計にしたか」を語ることの重要性 🧠

面接で最も評価が分かれるのは、「手順を覚えているか」ではなく「**なぜその手順・設計にしたのかを自分の言葉で説明できるか**」です。丸暗記した手順は深掘りの質問に弱く、「では、もし条件が変わったらどうしますか?」と聞かれた瞬間に答えに詰まってしまいます。逆に理由まで理解していれば、多少質問の角度が変わっても自分の頭で考えて答えられます。

以下は、各案件で「なぜ」を語れるようにしておきたい設計判断の例です。

| 案件 | 設計・判断 | 語るべき「なぜ」 |
|---|---|---|
| 案件01 | 全端末に静的IPを設定した | DHCPサーバーがまだ存在しない段階だったため。案件03でDHCPを構築してから動的割当に移行する、という段階的な設計の理由を説明できる |
| 案件02 | WAN区間に/30を使った | ポイントツーポイント接続はホストが2台だけで済むため、無駄なくアドレスを使い切れるから([docs/03_ip_address_design.md 3-5節](03_ip_address_design.md)参照) |
| 案件04 | VLANをVLSMで4分割した | 部門ごとに必要な台数が異なるため、均等分割より柔軟にアドレスを使えるから。総務・経理(/26=62台)と機器管理(/27=30台)で必要数が違う点を説明できる |
| 案件05 | DMZを設けた | 公開サーバーが攻撃を受けても、被害が社内LANの奥まで及ばないようにするため。ファイアウォールだけでなくネットワーク構成そのもので防御を分けた理由を説明できる |
| 案件07 | パスワード認証ではなく公開鍵認証を選んだ | 総当たり攻撃・パスワード漏えいのリスクを構造的に下げられるため |
| 案件08 | VRRP(keepalived)で冗長化した | 従業員50名規模になり、サーバー停止が業務停止に直結する経営リスクへ変わったため。冗長化のコストと得られる可用性のバランスを判断した経緯を語れる |

面接直前に慌てて用意するのではなく、**案件を終えた直後にその案件のREADME末尾「ポートフォリオ・面接でのアピールポイント」を自分の言葉で書き直しておく**と、後からまとめて思い出す負担がなくなります。

## 4. 演習の証拠を残す:スクリーンショットの活用 📸

設計書やREADMEだけでも学習の証明にはなりますが、**実際に手を動かした証拠(スクリーンショット)**があると説得力が大きく変わります。面接で画面共有をしながら「ここでこう失敗して、こう直しました」と見せられると、口頭だけの説明よりも圧倒的に伝わりやすくなります。

### 4-0. 本人の実施・判断を記録する

画像だけでは実施者・日時・対象が分かりにくいため、案件ごとに次の短い記録を添えます。これは未記入のテンプレートです。AIが生成した出力や教材の期待出力を実行証跡として使わず、本人が実行して得た結果を記録してください。

| 項目 | 記入内容 |
| --- | --- |
| 実施状況 | 未着手は `NOT RUN`、前提不足は `BLOCKED`、期待結果と異なる場合は `FAIL`、一致を確認した範囲だけ `PASS` |
| 実施日・案件・環境 | 本人の実施日、案件番号、VMまたはシミュレーター、対象ホスト、バージョン |
| 行ったことと支援 | 本人が操作したこと、AIや第三者が提案・確認したこと |
| 設定を選んだ理由 | 要件と別案を踏まえた本人の理由 |
| 確認できたこと | 期待値、実際の出力、終了コード、ログ・画像の保存先。HTTPは本文も確認する |
| 切り分けと戻し方 | 最初の仮説、外れた後に調べたこと、変更を戻す手順と実施したかどうか |
| 説明と残る課題 | 資料を閉じて説明した日・説明できた点・詰まった点、未実施の範囲 |

失敗や判断の変更をまだ経験していない場合は「該当する実施なし」と記載します。学習目標や面接例から本人の経験を作り足す必要はありません。

### 4-1. 保存場所のルール

各案件フォルダに `images/` フォルダを作り、その中に保存することを推奨します。

```text
projects/
└── case04_vlan_segmentation/
    ├── README.md
    └── images/
        ├── 01_packet_tracer_topology.png       # 構成図全体
        ├── 02_vlan_config_command.png           # VLAN設定コマンド実行結果
        ├── 03_ping_success_vlan10.png           # VLAN10内でのping疎通確認
        ├── 04_ping_fail_before_fix.png          # トラブル発生時(わざと失敗させた状態)
        └── 05_ping_success_after_fix.png        # 対処後の疎通確認
```

### 4-2. 撮っておくべき場面

| 場面 | 撮る理由 |
|---|---|
| 構成図・トポロジー全体 | 何を作ろうとしていたのかが一目で伝わる |
| 設定コマンド実行直後の画面 | 実際に自分の手で設定したことの証拠になる |
| 動作確認(ping・nslookup・curlなど)が成功した画面 | 「作って終わり」ではなく検証まで行ったことを示せる |
| わざと失敗させたときのエラー画面 | トラブルシューティング経験があることを示す最も説得力のある証拠 |
| 対処後に成功した画面 | エラー→対処→解決という一連の流れをセットで示せる |

ファイル名は `連番_内容` のように統一しておくと、あとで見返すときにもREADMEに埋め込むときにも扱いやすくなります。README内に画像を貼る場合は、Markdownで以下のように記述します。

```markdown
![VLAN10でのping疎通確認](images/03_ping_success_vlan10.png)
```

> ⚠️ 実機の画面をスクリーンショットする際、実在する社名・個人名・実際のグローバルIPアドレスなどが偶然写り込んでいないか確認してから保存してください。このパックでは実在の組織を指さない `203.0.113.0/24` のみを例示用グローバルIPとして使用しています([docs/03_ip_address_design.md](03_ip_address_design.md)参照)。

## 5. 面接でよく聞かれる質問と回答の方向性 💬

未経験からのインフラエンジニア志望者が実際によく聞かれる質問と、このパックのどの案件の経験を使って答えると説得力が出るかをまとめました。丸暗記した回答文をそのまま話すのではなく、下記を「自分の言葉に置き換えるための材料」として使ってください。

### Q1. なぜインフラエンジニアを目指したのか

**方向性**: 志望動機は本来ポートフォリオとは別に用意するものですが、「学習の過程で何に面白さを感じたか」を絡めると説得力が増します。案件01〜03で「見えない通信の流れが、設定ひとつで目に見えて変わる」体験をしたことや、案件08で「止まらないシステムを支える仕事」に興味を持った、といった具体的なきっかけを挙げると、他の未経験者と差別化しやすくなります。

### Q2. このポートフォリオで一番苦労した点は

**方向性**: 「難易度が高かった案件」をそのまま答えるのではなく、**具体的にどこでつまずき、どう解決したか**まで話すことが重要です。例えば案件04(VLAN分割)で「VLSMのサブネット計算を最初は均等に4分割してしまい、機器管理用VLANに対して余分なアドレスを割り当てすぎていたことに気づいて設計をやり直した」といった、失敗→気づき→修正のプロセスを語れると評価されやすくなります。案件09(集大成)は総合力が問われるため、統合作業でのつまずきも語りやすい題材です。

### Q3. VLANとサブネット(IPアドレス設計)の違いを説明してください

**方向性**: 「VLANはL2(スイッチ内)の論理的な分割、サブネットはL3(IPアドレス)の分割」という技術的な整理に加え、案件04の実例(本社LAN 192.168.10.0/24をVLAN10・20・30・99に分割し、各VLANに異なるサイズのサブネットを割り当てた)を使うと、単なる定義の暗記ではなく実際に設計した経験として語れます。「VLANで論理的にネットワークを分け、そのVLANごとにサブネット(IPアドレスの範囲)を割り当てる、というセットで初めて意味を持つ」という関係性まで説明できると理解の深さが伝わります。

### Q4. 静的ルーティングと動的ルーティングの違いは何ですか

**方向性**: 案件02で本社-支社間に静的ルートを設定した経験をもとに、「拠点数が少なく経路変更も頻繁ではない構成では、静的ルーティングの方が経路を把握しやすく、意図しない経路変更のリスクも少ない」という判断理由を説明します。あわせて「拠点数が増えたり経路が複雑になった場合はOSPFなどの動的ルーティングが選択肢になる」という発展的な視点も添えると、知識の幅を示せます。

### Q5. NATとファイアウォールの違いは何ですか

**方向性**: 案件05の経験から、「NAT/PATはプライベートIPとグローバルIPを変換する仕組みそのもの、ファイアウォールは通していい通信とダメな通信を判断する仕組み」という役割の違いを説明します。実務では家庭用ルーターのようにNAT機能とファイアウォール機能が1台の機器にまとまっていることが多いため、「機能としては別物だが、同じ機器に同居することが多い」という実態にも触れられると理解の深さが伝わります。

### Q6. 障害対応やトラブルシューティングで意識していることは

**方向性**: 各案件のREADME「よくあるトラブルと対処法」に沿って、案件01の疎通確認(ping)から案件08のtcpdump/Wiresharkまで、**下位レイヤーから順番に切り分けていく**という考え方を説明します。特に、意図的に設定を間違えてトラブルを体験する演習を繰り返したことで、「まずケーブル・物理層を疑い、次にIP設定、その次に上位のサービス設定」という切り分けの型が身についたと語れると説得力があります。

### Q7. なぜ独学でこの学習方法を選んだのか

**方向性**: 座学だけでなく「架空の依頼に対応する」というストーリー形式にした理由(実務に近い順序で「要件定義→設計→構築→動作確認→トラブル対応」を体験するため)を説明します。あわせて、資格学習(CCNAなど)だけでは得にくい「手を動かして構築し、失敗し、直す」という経験を重視したことも伝えられます。

### Q8. このポートフォリオの中で一番自信のある案件はどれですか

**方向性**: 本人が実施して結果を残した案件から一つ選びます。案件09が未実施であれば、完了した小さな案件で十分です。自分が操作したこと・設定の理由・確認した出力・残る課題を具体的に一つずつ説明してください。

## 7. GitHubの使い方のコツ 🐙

ポートフォリオの中身だけでなく、**GitHubの使い方そのもの**も見られています。以下は最低限意識しておきたいポイントです。

| ポイント | 理由 |
|---|---|
| コミットは小さく分ける | 「案件01: L2スイッチ・ルーター設定を追加」のように意味のある単位でコミットすると、作業の過程を採用担当者が追いやすくなる。1案件を1コミットでまとめて上げてしまうと、途中経過が見えず「一気にコピーしたのでは」という印象を与えかねない |
| コミットメッセージを具体的に書く | 「更新」ではなく「案件04: VLAN99(機器管理)のサブネットを/27に修正」のように、何をなぜ変えたかが分かる文にする |
| READMEを常に最新の状態に保つ | READMEはリポジトリの「顔」。ディレクトリ構成や案件一覧を変更したら、必ずREADMEも合わせて更新する |
| .gitignoreを設定する | Packet Tracerの一時ファイルやOS固有のファイル(`.DS_Store`など)がリポジトリに混入しないようにする |
| 大きすぎる添付ファイルに注意する | スクリーンショットは容量を圧縮する、動画は外部サービスにアップロードしてリンクを貼るなど、リポジトリを軽く保つ工夫をする |
| Issuesやプロジェクトボードを使ってみる(発展) | 「案件09で追加すべき項目」をIssueとして立て、対応したらクローズする、といった運用ができると実務のチーム開発に近い経験として語れる |
